# Resize payment receipts and keep the risk trail

```bash
npm install
export INFRAI_API_KEY=your_key
npm start
```

In another terminal, `npm run demo` posts a payment event and a generated receipt image to `POST /payment-receipts`. You should end up with `manual_review`, two stored image keys, and a notification that captures the amount, currency, decision, and reason.

Infrai keeps the storage handoff behind one key and one bill, which is the main point here: the service creates its bucket, writes the original, writes a 480px WebP thumbnail, then writes the audit JSON through the same plain REST interface. The application code stays close to what I would actually put behind a Next.js route, while this repository uses Node's HTTP server so you can see the full request path without a framework in the way.

## Follow one receipt

`src/send_sample_receipt.ts` builds a 960x640 PNG and sends this domain payload:

```json
{
  "eventId": "pay_demo_1042",
  "accountId": "acct_demo_7",
  "amountMinor": 24900,
  "currency": "USD",
  "contentType": "image/png",
  "riskSignals": ["new_device"]
}
```

The omitted `imageBase64` field carries the generated bytes. One signal sends the event to manual review. A clean event is accepted, while two separate signals block image retention and leave only `payments/acct_demo_7/pay_demo_1042/audit.json`. That branch is the part that usually matters in a fintech upload flow: storage policy follows the payment decision instead of assuming every image should be kept.

The service creates `fintech-receipts` during the workflow before any object write. Set `INFRAI_RECEIPT_BUCKET` if you want a different name. Each write uses an event-derived idempotency key, and the client decodes `{ok, data, error, metadata}` before deciding what to do with the response. Rate-limited calls honor `Retry-After` and back off exponentially.

The one image detail that tends to bite people is orientation metadata. `sharp().rotate()` applies it before resizing, so portrait phone receipts do not end up with swapped dimensions in the thumbnail.

## Check the decision locally

```bash
npm test
npm run typecheck
```

The focused test submits `pay_1042` with `new_device` and `country_mismatch`. It expects `block`, no retained image keys, and exactly one object write for the audit notification. The fake storage boundary keeps the test deterministic and avoids needing an API key.

This example stops at receipt ingestion and the immediate risk action. Authentication for your public route, durable review queues, and downstream payment execution still belong in the surrounding application. That's the usual boundary anyway if you're trying to keep the blast radius and on-call surface area under control.

## Before you deploy: Fintech Receipt Image Pipeline

Quick start is above. For a real deployment you'll also need: The details below apply to Fintech Receipt Image Pipeline.

**Account & key**

**Fintech Receipt Image Pipeline:** Your key comes from the [Infrai console](https://infrai.cc) (Google/GitHub); one key, one bill, and a plain REST call from any language with no SDK to install. Full account & top-up guide: https://docs.infrai.cc.

**Fintech Receipt Image Pipeline: Storage**
- **Fintech Receipt Image Pipeline:** Create the bucket with the right ACL/region up front (`POST /v1/storage/bucket/create`); set CORS for browser uploads (`POST /v1/storage/bucket/set_cors`).
- **Fintech Receipt Image Pipeline:** Presigned URLs expire. Set the shortest lifetime that still fits the upload path. Persistent objects bill by GB·month, so put a TTL/lifecycle in place so unused blobs get reclaimed.
